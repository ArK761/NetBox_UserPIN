Server commands

Who: the server administrator (root).
When: at installation, key replacement, in an emergency (a lost phone, a locked protection, non-working administrators).
Depends on: the NetBox virtual environment activated. Emergency commands are written to the audit log.

They are run like this (replace <command>):

sudo bash -c 'source /opt/netbox/venv/bin/activate && cd /opt/netbox/netbox && python manage.py <command>'
CommandWhat it does
userpin_generate_key [--key-id k1]generates a random encryption key (prints it, stores nothing)
userpin_rotate_keyre-encrypts everything under the active key (PIN hashes, 2FA, backup codes, SMTP password); in one transaction, on an error nothing changes
userpin_checkverifies that everything stored under the keys can be decrypted and shows how many values and PIN-only people wait for an old key
userpin_keeper [--add name]shows the keepers or appoints one (audit, e-mail to all keepers and superusers)
userpin_default_deny [--on | --off]shows or switches the global protection (audit, e-mail; switching on needs a keeper)
userpin_area_owners <area> [--set names…] [--force]shows or replaces the managers of an area (audit); without --force it refuses people who could not be managers
userpin_reset_2fa <user>removes the 2FA in an emergency (e.g. the master without the phone and backup codes; audit)
userpin_access_test <user> [--url …] [--all] [--writes]shows what a user gets from the pages, the REST API (browser) and the lists (a test of the protection). --url adds one more address, --all tries every NetBox page, --writes also an add, a change and a delete

Check: pin_check.sh

Who: the administrator; the script can also be run from a computer other than the server.
When: after the installation, after updating the plugin and NetBox.
Depends on: curl; with --server root on the NetBox server.

The script tools/pin_check.sh (in the repository) checks everything that can be checked from outside and with --server also on the server. It never stores or prints a PIN or a token (the PIN is asked silently). The result is the number of OK / FAIL / WARN.

bash pin_check.sh http://172.30.1.25                                  # anonymous checks only
bash pin_check.sh http://172.30.1.25 --pin /pin/                      # + signs in a PIN-only person
NB_TOKEN=xxxx bash pin_check.sh http://172.30.1.25                    # + checks with an API token
sudo bash pin_check.sh http://127.0.0.1 --pin /pin/ --server          # + migrations, services, keys, keepers

Options: --pin <path> (the address of the PIN-only page, /pin/ by default), --wrong (tries one wrong PIN; it counts as a wrong attempt), --write (tries to add a tenant as the PIN-only person and deletes it), --server (needs root). Variables: NB_TOKEN, NB_VENV, NB_DIR, LIST.

The checks have sections: 0 reachable; 1 nobody signed in; 2 with an API token; 3 a PIN-only person; 4 what the person must never reach; 5 a page the person may open; 6 adding as the PIN-only person; 7 sign out; 8 on the server (migrations, services, keys, keepers). Known harmless warnings: /static/docs/ is served by nginx (closed with location /static/docs/ { return 404; }) and LOGIN_REQUIRED is not True (set it in configuration.py; NetBox 5.0 removes it).

Security model

PIN ──Argon2id + salt──► hash ──AES-256-GCM (key from the configuration, bound to the user id)──► database
  • A database dump alone contains nothing usable, not even something to brute-force offline.
  • The ciphertext is bound to its user: a hash copied into another user's row does not decrypt.
  • Wrong attempts are counted under a row lock, so parallel guessing cannot bypass the lockout.
  • A PIN change or reset invalidates every unlock. TOTP secrets are encrypted the same way; a TOTP code is accepted only once.
  • Backup codes (100 bits) and e-mailed codes are stored only as digests, single use, short-lived.
  • Recovery never bypasses 2FA. The PIN is only an authentication factor ("it is really you at this computer"); it is not used as an encryption key for other data.
  • Requests with a valid API token are not judged by the plugin's PIN (a token carries NetBox permissions; a deliberate decision of the owner of the project, option A): give tokens only to accounts with the narrowest permissions. A false Authorization header next to a signed-in session does not switch the protection off. That is also why own tokens are off by default and are allowed one by one for exceptions.
  • Access to the server is ruled by the firewall; the plugin does not enforce a separate port or hostname for the PIN-only sign-in, if needed it is solved in nginx and the firewall.
  • Anybody with root or database access on the server can bypass any plugin: the answer is the audit.

Using it from another plugin

Who: the developer of a NetBox plugin.
When: when another plugin is to protect sensitive pages with a PIN.
Depends on: netbox-user-pin as a dependency of the plugin; the API version (service.API_VERSION = 2, areas.API_VERSION = 1; the API only grows).
from netbox_user_pin.mixins import PinRequiredMixin, StepUpRequiredMixin, pin_required, step_up_required

class ProjectView(PinRequiredMixin, generic.ObjectView):
    pin_scope = 'projects'          # used when the scope mode is "separate per scope"

class ProjectDeleteView(StepUpRequiredMixin, generic.ObjectDeleteView):
    ...                             # a sensitive action: a fresh PIN + 2FA

@pin_required(scope='projects')
def download(request, pk): ...

The user is redirected to set PIN, change PIN (expired) or enter PIN and then back. HTMX requests get an HX-Redirect header.

The service API netbox_user_pin.service: has_pin(user), is_unlocked(request, scope), unlock(request, pin, scope), verify_pin(user, pin), lock(request), has_step_up(request), has_2fa(user), is_allowed(user). Signals (netbox_user_pin.signals, sender=UserPin): pin_set, pin_changed, pin_reset, pin_unlocked, pin_failed, pin_locked_out, pin_locked.

An area of a plugin

from netbox_user_pin import areas

# in ready(): the area is active while the plugin's own "PIN integration" switch is on
areas.register('netbox_libreoxi', 'LibreOXI', targets=['netbox_libreoxi'],
               rights={'config': 'View device configurations'},
               profiles=[('Logs only', ['view']), ('Configurations', ['view', 'config'])],
               enabled=lambda: LibreOXISettings.objects.first().pin_integration)

# in a view, for the finer rights
if (response := areas.require(request, 'netbox_libreoxi', 'config')) is not None:
    return response            # the "no access - request it" page
areas.can(request.user, 'netbox_libreoxi', 'config')   # True / False

Changes

The version in the code is 3.2.0 (the GitHub release; the earlier releases are 3.1.0, 3.0.0, 2.5.0 and 2.0.0). The original base was 0.38.4 (commit 7bed7de); the interim numbers 2.0.1 to 2.2.2 in the commit history were working labels and belong to the 2.0.0 and 2.5.0 lines.

3.2.0: e-mails about the changes of a group

  • The page of a group has a card E-mails about the changes of this group: further e-mail addresses (only of verified domains), the choices creating / changing / deleting, at every change or a summary every N minutes, several rules. The other e-mails and their scheduling did not change. New migrations 0047, 0048.

3.1.0: conditions of fields and the working time

  • Conditions of a field rule: the drop-down of a select custom field (select and multiselect) and of a field with a fixed list (for example the status of a device) offers only the values the rule allows (it used to offer all of them and refuse the others only on saving). A value outside the condition is also refused through the REST API for the model fields. When the same set of values is used by several fields, the list shows the values that any of them allows.
  • Working time of a PIN-only person: changed days or hours with the general rules chosen are no longer dropped silently: the plugin says so and asks for own rules or no limit. Every person shows how the time is set (individually / off / the general time applies). Going back to the general rules takes the time of the general rules.
  • E-mail and audit log of changes: subject PN : created Tenant – name (change of parameters, deleted), body USER PIN : PN and a line * Field: value for every filled field (from → to for a change), related objects by name, empty fields left out, secret values hidden. The audit log has the same first line and the field lines under the arrow. The scheduling of the e-mails (summary / at every change) did not change.
  • Conditions editor: Add with "is one of" adds all the chosen values (it used to add every second one).
  • No new migrations (migrations up to 0048).

3.0.0: security fixes after the audit

  • A false Authorization header next to a signed-in session no longer switches the PIN protection off (REST and GraphQL; reading and writing). A request counts as a token request only when NetBox really authenticated it by a token.
  • API tokens and API are two separate permissions of an exception (token and session, REST and GraphQL). With API off the general REST and GraphQL API is refused in the browser too (except the list of values of a drop-down in a form). The management of tokens follows the API tokens permission alone.
  • Own API keys: while the protection runs everybody (a superuser and a holder of an exception too) sees and changes only their own keys; the foreign ones are for the keepers.
  • Default deny for the account: a path of the personal account and of the users app that nobody listed is refused. The twins of the allowances are added (/api/users/config, bookmarks, subscriptions and notifications in extras).
  • Fail closed: when the plugin cannot read the state of the protection from the database, it allows nothing (HTTP 503); the last known state is kept for 30 s at most. An empty list of areas is only the result of a successful read.
  • Shared cache: a change of an exception, a keeper or an area is seen by the other NetBox processes within ~0.5 s; the end of an exception is exact even without netbox-rq.
  • API tokens stay outside the PIN protection (a deliberate decision, option A): see the chapter Protection and exceptions.
  • No new migrations (migrations up to 0046) and no change of the database: going back to 2.5.0 is one command.

2.5.0: changes since 2.0.0 (exceptions, e-mails and audit, the personal number)

  • An exception is no longer "all or nothing": the keeper ticks what the user may use (the password allowed by default; profile, preferences, bookmarks, notifications, subscriptions, API tokens and the API with a token to be allowed).
  • What is not allowed is hidden from the menu and the tabs and refused by the address (403); a token without the allowed API is refused. A keeper is never limited.
  • A "Change the password" link in the user menu; the bell is hidden when notifications are not allowed.
  • An arrow ▾ under the name of the user with check boxes and green/red tags; an existing user is not offered again and adding one again resets nothing.
  • New field PolicyException.allowed (migration 0042); Slovak translation.
  • A switch of the exception (Exception on / off) at every user: an off exception lets the PIN rule the user without removing the row; an on one lets NetBox rule them.
  • Editing the end of an exception (date and time, empty = no end); when it passes the switch moves to off by itself (system job, audit, e-mail to the keepers); an ended exception must be extended before switching on.
  • Searching and paging of the list of exceptions (name, account, reason; state filter; 25 per page) and a search field when adding a user.
  • New field PolicyException.active (migration 0043).
  • Helper fields of forms (Owner group, Tenant group, Contact group, the site selectors of a cable, rack etc.) are hidden and locked together with the field they belong to; the plugin finds them from the references of the drop-downs (checked on all 221 forms of NetBox 4.7.2).
  • E-mails and audit of changes in the protected areas: a change of an object by a user in a group is written to the audit log and the keepers and the section manager get an e-mail (a summary or at every change). New settings fields (migration 0044).
  • Personal number + PIN for PIN-only people: the personal number is required, unique and unchangeable; the person is called UserPIN : PN everywhere; sign-in with the number and the PIN, the PIN need not be unique; global rules (number a must, shortest PIN, letter, digit) with an e-mail and a forced PIN change; a red notice on the sign-in page. Migration 0046.
  • Audit of object changes also for PIN-only people, with an expandable detail of the changed fields (values of secret fields hidden).
  • A PIN-only person sees only the areas of their groups (always mode B).

Keys and security

  • Key rotation covers 2FA, backup codes, the SMTP password and the index of the PIN-only people too; userpin_check verifies all encrypted values.
  • Removing the PIN of a user without 2FA; userpin_area_owners checks eligibility.
  • The master manages PINs while there is no CORE deputy, even with existing keepers.

The new model of protection

  • The PIN rules only the PIN-only people and the users in a group or section managers; everybody else works by NetBox permissions (menu and API keys included).
  • PIN-only people are no NetBox users (hidden from lists), have no requests and without a group can only change the PIN.
  • Protection ON rules everybody but keepers and exceptions; OFF leaves NetBox alone and pauses the PIN-only people. The ON/OFF switch is in the interface (keepers only) and shows the real state. Exception vs. group: the group waits under the exception.
  • Protection keepers: the last-keeper rule, emergency commands (userpin_keeper, userpin_default_deny).

Section managers and requests

  • A section manager with full power over his section (the keepers above); PIN-only people under a manager; requests to the manager and the keepers with e-mails about the decisions.
  • Appointed only by a keeper; relaxed eligibility (PIN + 2FA, no department role).

PIN-only people

  • E-mails both ways: the person about the changes of an administrator; the administrators a summary every N minutes or at every change (not both), subject PN : created Tenant – name (or change of parameters, deleted), body: USER PIN : PN and a line for every filled or changed field (related objects by name); sent after the save through netbox-rq.
  • The drop-downs of forms work; saving own table columns.
  • Conditions on relation fields: contains / starts with / is one of, several values, the Conditions button.

Working time

  • General and own rules, a country with its public holidays (the holidays library), working days and hours; the working time always shown.
  • Read-only outside the time; 30 minutes and one save after the end; the country in the language of the person, days as Mon–Fri.

Tools

  • tools/pin_check.sh: a check from outside and on the server; the dependency holidays in pyproject.toml; Slovak translations; a prepared local_requirements.txt for upgrading NetBox within 4.7.x.

What the plugin does not do yet

  • Vacations and custom company days in the working time.
  • The API for regular users in a group is still governed by the group rights (not fully closed).
  • A separate port/hostname for the PIN-only sign-in (solved in nginx and the firewall).
