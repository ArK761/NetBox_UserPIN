Protected areas

Who: the page Protected areas is seen by a protection keeper, a section manager and (while there is no keeper) CORE / the master. Areas are created and targets added only by a keeper (while there is none, CORE / the master). Groups, fields and members are managed by a keeper or the manager of the section.
When: when a part of NetBox (an app or an object type, e.g. DCIM › Device, Tenancy › Tenant) is to be seen and changed only by those who have been given access.
Depends on: the protection switched on (the Protection chapter), at least one keeper, section managers with a PIN and 2FA, and for requests mail (the E-mails chapter).

The basic idea

An area protects an object type (dcim.device) or a whole app (dcim). In a protected area nobody is a god: the plugin does not take the role or the NetBox permissions of the user into account at all, the group into which a keeper or a section manager put the user decides, even for a superuser. The door (a menu entry, a tab) stays visible for everybody; whoever has no key is refused on entering and learns who manages the access (the page "This area is protected"). Sensitive apps (users, auth, core etc.) can be put into an area only by a keeper.

The Protected areas page

  • The Protection card: the ON/OFF state and the switch (the Protection chapter).
  • Protection keepers, Exceptions, What the users see: the Protection chapter.
  • What is set up: the list of protected apps and object types. Each has the number of members, groups, managers (no owner yet) and the buttons Open and Delete (Remove the protection of this object type? Its groups and accesses are deleted.).
  • Add an app or an object type: choose from the list and Add. Adding only prepares the structure: nobody gets access until you create a group and put users into it. Until an area has a manager only the keepers see it.
  • At the top is the number of access requests waiting for your decision. If the protection of your own areas is off the page says so (Settings → Protected areas); areas of plugins with a "PIN integration" protect as soon as the plugin's integration is switched on.

A group is for one object type. A user is in one group per type: adding him to another moves him and leaving the last one means no access. An access can be temporary (until) or unlimited; a temporary one lasts from 1 hour up to Longest temporary access hours. A user may end their own access (My access → End my access); others' are removed by a keeper or a manager.

A group: the records it sees

OptionMeaning
Not set (sees no record)the starting point: the members see no row
All recordsthe members see all rows of this type
Only by conditionsthey see only the rows that match the conditions
  • Allowed: several values of one condition are alternatives (agg or core); several conditions must all hold at once. With no condition the group sees nothing.
  • Denied: records that match any of these conditions are never shown, whatever else allows them.
  • A condition = a field + an operator + a value. Operators: is, is not, contains, does not contain, starts with, is one of, is not one of. For a field with choices or a relation the values are chosen from a list.

Fields

For a group (or for everybody in the area) and an object type every field is:

ModeMeaning
By rights (default)whoever may add or change sees and writes every field; a read-only user reads
Hiddenthe field is not shown to the user
Read onlyvisible, cannot be changed
Read and writevisible and changeable
  • The Fields page (Rules for a group or user + an object type): unfold the group and set field by field, or all at once with Set all shown fields (applies to the fields left by the search), then Save rules.
  • The option Hidden from everybody in the area hides the field from everybody in the area, managers included.
  • A condition on the values of a field (Values must include, or the Conditions button: contains, starts with, is one of; several values as chips) limits what the user may pick: in custom fields linked to other objects (for example devices whose name contains PRINTER), in select and multiselect custom fields and in fields with a fixed list (for example the status of a device). The drop-down offers only the allowed values, and a value outside the condition is refused on saving, in the form and through the REST API. When the same set of values is used by several fields, the list shows the values that any of them allows (and all of them if one of the fields has no condition).
  • A hidden custom field keeps its stored data (saving an object never wipes it).
  • Helper fields of a form. Some fields of a form are not fields of the model, for example Owner group next to Owner (it only narrows the choice of owners and stores nothing). They are not in the list of fields; they follow the field they belong to: hiding or locking Owner hides or locks Owner group too.

Tabs of the detail

The page Tabs of the detail page decides which tabs of an object's detail (Interfaces, Config Context, Changelog …) the user may open. The main page is always allowed. A new access allows only the main page. A section manager opens every tab.

An access request

  1. A user whose way is closed sees the page "This area is protected" (who manages the access, what was blocked, what you can do here: Change the password, My PIN, My API keys). They tick what they need (view / add / change / delete), write why and what exactly (section, group, object) and press Request access.
  2. An e-mail with a link goes to the section manager and the keepers; if no area exists for the type yet, only to the keepers. The link opens the page Access request (who, what, why, when).
  3. The decider chooses the group to put the user into (or A new group with a name), the rights to grant and for how long, and presses Approve or Deny. If no area exists for the type yet, the approval creates it (without managers: they must be appointed by hand) and adds the user.
  4. The requester gets an e-mail about the decision (so do the keepers and the manager). A waiting request can be cancelled in My access → My requests.
  • Nobody decides about their own request. Only one request can wait per user, area and type.
  • Requests can be switched off (Users may ask for access): then only the administrators make them. PIN-only people cannot ask.
  • A user without a PIN is sent to create one on entering (no 2FA needed) and then continues.

My access

Menu My access: My access to protected areas (area, profile, until, End my access), the sections you manage and My requests (area, when, status, Cancel). At the top is the number of requests waiting for your decision.

Not covered: filters in lists (?cf_name=…), exports, the fixed fields of the detail and lists mixing several types. Anybody with root / database access on the server can bypass any plugin: the answer is the audit, not a technical lock.

An area of a plugin

A plugin can register its own area (areas.register(...)) with its own rights and profiles. It is protected when its "PIN integration" switch is on, even without the global Protect areas and objects. See the chapter Using it from another plugin.
